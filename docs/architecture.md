# Архитектура стартового примера

В примере два рабочих проекта и один проект тестов.

| Часть | Ответственность | Зависимости |
| --- | --- | --- |
| Findirector.Domain | Параметры, ограничения, финансовый расчёт и результат | Стандартная библиотека .NET |
| Findirector.Console | Учебные входные данные и текстовый вывод | Domain |
| Findirector.Tests | Проверки контракта на числовых примерах | Domain, xUnit |

`MonthPlan` — неизменяемые параметры с проверкой значений в конструкторе.
`MonthCalculator` — чистый расчёт: принимает данные и возвращает результат без внешних действий.
`MonthReport` — неизменяемый результат и производные финансовые показатели.
Внутренний `Money` проверяет точность и допустимый знак денежных входов.

Для изменения вывода достаточно править консоль. Для изменения финансового правила — Domain и его проверки.
Вызывающему коду не требуется знать способ расчёта каждого показателя.
Такая граница позволяет в следующих работах подключить UI и хранение.

## Дальнейшее развитие по лабораторным

В ЛР2 проектируются Domain, Application, Infrastructure и UI.
Там же создаётся логическая ER-модель плана и его трёх месяцев с описанием сохраняемых полей
в `docs/data.md`. Это будущие данные продукта; текущая диаграмма классов описывает только ядро ЛР0.
В ЛР3 Application организует расчёт трёх месяцев и сравнение планов, вызывая Domain.
Для хранения Application объявляет интерфейс; в ЛР4 Infrastructure реализует его через SQLite.
В ЛР4 та же ER-модель уточняется SQL-типами, ключами и ограничениями.
В ЛР5 Blazor вызывает операции Application. Сборка зависимостей выполняется в точке запуска приложения.

При расчёте полного плана Application каждый раз начинает с исходных денег и нулевой
задолженности, не изменяя параметры. При сравнении рассчитывает каждый план независимо.
Список, сохранение и открытие — операции интерфейса хранилища; идентификатор плана
сохраняется при редактировании. Расчётные отчёты можно восстановить из входов.

В текущем примере операция одна и не требует прикладной оркестрации, поэтому отдельный Application не создан.
Интерфейсов для всех классов, контейнера зависимостей и универсального репозитория здесь нет:
каждая дополнительная конструкция должна появляться вместе с задачей, которую она решает.
